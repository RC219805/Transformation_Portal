# Lux Depth Unification Audit — 2026-09-26

## Scope and evidence standard

This audit supports a canonical `transformation_portal.lux_depth` integration
surface across the existing Lux Depth implementations. The source baseline is
`cae2c264d69325e51a63d86488923a581f9e4e22`. It does not authorize a production
executor replacement, a new execution-plan schema, or removal of a versioned
entry point. LuxDepthV3 remains the production default and rollback path.

The companion [inventory](lux_depth_unification_inventory.json) records each
in-scope file's byte count, SHA-256, area, disposition, and review depth. Its
digest is a snapshot of the working file, with the baseline Git blob recorded
separately where available. It inventories every file in the live V3, V4, V5,
V6, and MaterialsV4 packages, selected shared authority and integration files,
and the named historical enhancement/rendering surfaces. Generated bytecode is
excluded. Archive ZIP members are listed from metadata without extraction or
execution; they are not live source authority.

Review depth is deliberately explicit: `full_source_review` means the assigned
auditor read the module; `boundary_review` means relevant execution, trust, or
data boundaries were inspected; `inventory_only` means discovery and hashing,
without a claim of source review. An inventory-wide digest does not prove every
line was audited. Referenced lines describe the baseline unless an implementation
update is explicitly identified. No photographic, performance, native runtime,
or hosted-service acceptance is inferred from source inspection or unit tests.

Every Python module in the 82-module V3, 16-module V4, 11-module V5,
16-module V6 and 11-module MaterialsV4 packages received at least boundary
review. For larger V3 modules, that means public definitions and selected
model/runtime, input, cache, artifact, error and validation control-flow excerpts;
it is not a claim that every line of those large modules was read. Tests,
supporting documents and adjacent depth implementations retain their separately
recorded review depth.

## Findings that determine the consolidation

1. **The missing capability is one public composition path.** Before this
   change, the V6 standalone CLI accepts retained V5 generations or Depth Pro
   research, while `lux_depth_v6/managed.py:89-132` already prepares a complete
   original-photograph DA3 → V5 → V6 execution. Reuse that existing core V5 plan
   and its exact embedded V5 plan for standalone composition. Reimplementing the
   pipeline in a facade would introduce a second authority.
2. **The historical `UnifiedLuxuryPipeline` is unsuitable as the precision
   authority.** `pipelines/unified_luxury_pipeline.py:863-895` converts uint16
   and floating TIFF pixels to uint8 RGB and drops alpha. The master writer
   later expands PIL pixels to uint16 (`:1524-1547`), which cannot restore
   discarded precision. Its depth stage writes a fixed-name lossy JPEG and
   returns the original image after processing errors (`:1034-1087`). Keep the
   compatibility surface; reuse the bounded parallel-I/O design only where
   independently justified, not this decode/master path.
3. **V3 prepared authority must remain intact.** The direct orchestrator
   constructor rejects cache-enabled execution; `from_prepared` reconstructs
   runtime config from the validated carried plan
   (`lux_depth_v3/orchestrator.py:646-669,879-901`). A unified compatibility path
   must invoke the existing CLI or prepared lifecycle, preserving discovery,
   the exact plan bytes, input authorization, and completion evidence.
4. **Materials are not universally composable with V6 finishing.** V5 supports
   frozen MaterialsV4 evidence. V6 rejects V5 sources with applied Materials
   because it cannot replay the absent retained masks
   (`lux_depth_v6/source.py:215-221`). Expose a distinct V5 inference/materials
   path; do not imply that this limitation disappears through a common import.
5. **Installed-package legacy enhancement remains a separate gap.** V3 enables
   V2 by default (`lux_depth_v3/config.py:240-244`), while `V2Runner` locates
   `scripts/enhance_image.py` through repository markers and refuses execution
   if the script is absent (`v2_runner.py:43-84,137-142`). This is a confirmed
   source dependency; an installed-wheel failure has not been reproduced in
   this audit. Do not describe the existing V3 compatibility path as proven
   independent of a checkout.

## Unified surface and authority boundaries

The selected architecture is an additive facade with explicit operations:

- **Process original photographs:** prepare and run the existing DA3 → V5 →
  V6 composite, preserving its core execution-plan V5 carrier, resource bounds,
  intermediate verification, and publication semantics.
- **Infer with optional Materials:** prepare and run existing V5, including its
  exact MaterialsV4 evidence contract, without pretending V6 accepts that result.
- **Finish a retained V5 generation:** reuse V6 preparation, execution and replay.
- **Depth Pro research:** reuse V6 research request, acknowledgements, runtime
  checks and evidence; keep it outside managed DA3 and governed DA3 cache reuse.
- **Verify:** use the verifier corresponding to the recorded existing carrier.
- **Legacy V3:** preserve existing production CLI/options, selectors, import
  exports, discovery behavior, result statuses, artifact names and run cards.

The facade owns operation selection and composition. Existing packages continue
to own algorithms, executable plans, identity, cache, publication and verification.
No unversioned envelope may replace a core plan, no CLI option may silently
select a different historical recipe, and a JSON projection alone does not grant
execution authority. `tp.crypto`, `tp.merkle` and Phase 4 evidence remain outside
operational consolidation. ADR-051 explicitly retains the live Lux executor
until applicable contract, security, output and performance gates pass
(`docs/architecture/ADR-051-execution-artifact-authority-designation.md:111-115`).

Input admission must happen before output creation and model work. In particular,
resource-limit validation must not disappear when reusing a formerly managed
composite through a standalone entry point. New import/help/plan paths must remain
usable without loading optional ML stacks. There is no default production
promotion, existing schema mutation, changed authentication policy, or replacement
of API/worker route names in this design.

## Weaknesses retained as explicit boundaries

- V4 evidence validation is less rigorous than V5 numerical replay
  (`lux_depth_v4/evidence.py:187-249` versus
  `lux_depth_v5/evidence.py:150-311`). Preserve V4 verification; use V5 as the inference
  authority for the new composite.
- Automatic source-color interpretation accepts the supported sRGB case and
  rejects ambiguity (`lux_depth_v4/photography.py:74-100`). A common CLI must
  not silently guess an ICC/color transform.
- V5 public requests expose the original bilinear/guided-bilinear recipe choices
  (`lux_depth_v5/lifecycle.py:102-116`). Newer low-level recipes retained for
  V6 are not permission to change historical V5 plans.
- Depth Pro meters are model estimates. Its numeric-validity mask does not
  establish surface/sky correctness; without the required evidence it abstains
  from depth edits. V5 unknown-sky states similarly abstain.
- Native runtime, governed-cache/optional-input behavior, representative
  photographs, source camera authenticity and perceptual quality need their own
  acceptance evidence. Synthetic fixtures and successful semantic replay do
  not establish photographic superiority.
- The source ZIP and archived `lux_render_pipeline_plus_v3.py` are historical
  references. They neither override live contracts nor justify copying code
  without review and regression coverage.

### Legacy helper findings retained for scoped hardening

These are source-observed limitations of legacy helpers, not newly demonstrated
managed-route exploits. They are reasons to retain the stronger prepared,
supervised and published V5/V6 paths in the canonical composition:

| Boundary | Observed behavior | Implication |
| --- | --- | --- |
| PBR preset retrieval | `lux_depth_v3/pbr_presets.py:212-234` returns a mutable `EnhanceConfig` directly from global `PRESETS`. | Mutating a returned preset changes later retrievals in the same process; callers need independent configuration snapshots. |
| Legacy DA3 model loading | `lux_depth_v3/inference.py:581-589` retries an incompatible `from_pretrained` call without the revision unless strict locking is enabled. | This compatibility fallback is not evidence of a pinned native execution; governed V5/V6 worker authority must remain separate. |
| Segmentation cache publication | `lux_depth_v3/segmentation/_cache.py:394-412` uses fixed `.npz.tmp` and `.json.tmp` filenames and separate replacements without the governed depth-cache locking protocol. | This cache cannot be promoted to concurrent generation or governed depth-cache authority. Concurrent-writer failure was not reproduced here. |
| Low-level depth writer | `lux_depth_v3/contracts/depth_artifact.py:432-478` writes arrays/sidecars directly using caller-supplied stems. | It is a trusted-caller helper, not a confined generation publisher. Do not expose raw stems as managed authorization. |
| Segmentation fallback/confidence | `lux_depth_v3/segmentation/efficient_sam.py:277-300` permits an explicit heuristic fallback; `material_confidence_contract.py:12-23` separates authorizing scores from heuristics. | A fixed heuristic score or SAM mask quality is not semantic material confidence. Preserve refusal/abstention and the MaterialsV4 evidence path. |
| Partial PBR output | `lux_depth_v3/pbr_writer.py:79-88` raises only if every map write fails. | Completeness belongs to the prepared execution's required-artifact verifier, not this helper's return status. |
