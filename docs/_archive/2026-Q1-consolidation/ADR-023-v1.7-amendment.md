# ADR-023 Amendment: Performance Ledger v1.7 Upgrade

**Status:** ACCEPTED
**Date:** 2026-02-05
**Amends:** ADR-023 (Performance Ledger Implementation)
**Decision Authority:** Transformation Portal Architect

---

## Context

Performance Ledger v1.0 (implemented per ADR-023) has been in production since January 2026. This amendment documents the v1.7 upgrade that addresses deployment constraints and enhances robustness while maintaining backward compatibility.

### Motivation for v1.7

1. **Deployment Flexibility:** NumPy is a large dependency (~50MB). Some CI environments prefer minimal installs.
2. **Statistical Rigor:** Bootstrap confidence intervals provide uncertainty quantification for mean estimates.
3. **Operational Safety:** Backend mismatch detection prevents comparing incompatible runs.
4. **Resource Protection:** Input validation bounds prevent DoS via excessive iterations.
5. **CI Integration:** Expanded exit codes enable more nuanced failure handling.

---

## Decision

Upgrade Performance Ledger to v1.7 with the following enhancements:

### 1. Optional NumPy Dependency

**Change:** NumPy becomes optional with pure Python fallback.

**Rationale:**
- Enables deployment in minimal CI environments
- Reduces attack surface (one less compiled dependency)
- Pure Python mode sufficient for small datasets (< 50 samples)

**Implementation:**
```python
try:
    import numpy as np
    HAS_NUMPY = True
except ImportError:
    HAS_NUMPY = False
    # Use pure Python implementations
```

**Performance Impact:**
- NumPy mode: No change from v1.0 (< 5ms for 50 samples)
- Pure Python mode: 50x slower (acceptable for < 20 samples)
- Recommendation: Install NumPy for production use

**Validation:**
- Property-based tests validate pure Python math matches NumPy within 1e-8 relative error
- 100+ Hypothesis test cases per function (mean, std, percentile)

---

### 2. Bootstrap Confidence Intervals

**Change:** Add optional bootstrap CI for mean with configurable iterations.

**Rationale:**
- Quantifies uncertainty in performance measurements
- Detects when sample size is insufficient for confident conclusions
- Standard statistical technique (widely validated)

**Default:** 1000 iterations (95% CI)

**Usage:**
```bash
# Default: 1000 iterations
python tools/performance_ledger.py --manifests-dir ./manifests --output baseline.json

# Custom iterations
--bootstrap-iterations 5000

# Disable (faster)
--no-bootstrap
```

**Output Schema Extension:**
```json
{
  "statistics": {
    "mean_sec": 10.0,
    "bootstrap_ci_95_lower": 9.7,
    "bootstrap_ci_95_upper": 10.3
  }
}
```

**Performance Cost:**
- 100 iterations: ~10ms
- 1000 iterations: ~50-100ms (default)
- 5000 iterations: ~500ms
- Max allowed: 10,000 (DoS prevention)

---

### 3. Expanded Exit Codes

**Change:** Expand from 2 to 4 exit codes for operational clarity.

**v1.0 Exit Codes:**
```
0 = Success (no regression)
1 = Regression detected
```

**v1.7 Exit Codes:**
```
0 = Success (no regression or potential regression without --strict)
1 = Significant regression detected
2 = Backend mismatch (incomparable runs)
3 = Insufficient data (< 3 samples or validation failure)
```

**Rationale:**
- Exit code 2 prevents false positives from comparing DA3 vs DepthPro
- Exit code 3 distinguishes data quality issues from performance issues
- Exit code 0 with `--strict` prevents gradual performance erosion in CI

**CI Recommendation:**
```bash
python tools/performance_ledger.py \
    --baseline baseline.json \
    --compare ./current \
    --output report.md \
    --strict  # Fail on potential regressions

exit_code=$?
case $exit_code in
    0) echo "✅ Performance OK" ;;
    1) echo "❌ Regression detected"; exit 1 ;;
    2) echo "⚠️  Backend mismatch"; exit 1 ;;
    3) echo "⚠️  Insufficient data"; exit 1 ;;
esac
```

---

### 4. Backend Mismatch Detection

**Change:** Detect when baseline and current run use different depth backends.

**Rationale:**
- DA3 and DepthPro have different performance characteristics
- Comparing across backends produces meaningless results
- Prevents CI false alarms when backend changes

**Implementation:**
- Extracts backend from `manifest.depth.model`
- Normalizes aliases (e.g., "da3" == "depth-anything-v3")
- Returns exit code 2 if > 0% mismatch

**Example:**
```
Baseline: da3 (100 samples)
Current:  depth-pro (100 samples)

ERROR: Backend mismatch: 100.0% samples differ from baseline 'da3'
Exit code: 2
```

---

### 5. Input Validation Bounds (DoS Prevention)

**Change:** Enforce maximum values for resource-intensive parameters.

**Bounds:**
```python
MAX_BOOTSTRAP_ITERATIONS = 10000  # Prevent CPU exhaustion
MIN_SAMPLES_FOR_COMPARISON = 3    # Require statistical validity
```

**Rationale:**
- Prevent accidental or malicious resource exhaustion
- `--bootstrap-iterations 1000000` would hang for minutes
- 3-sample minimum ensures percentiles are meaningful

**Validation:**
- CLI tests verify rejection of excessive values
- Error messages guide users to valid ranges

---

### 6. Backward Compatibility (Condition #1)

**Change:** Deprecate `--version` flag, add `--baseline-version` as replacement.

**Migration Path:**

**Phase 1 (v1.7 - v1.9):** Both flags work
```bash
# Deprecated but functional
--version v2.0.0  # Logs warning

# Preferred
--baseline-version v2.0.0
```

**Phase 2 (v2.0+):** Remove `--version` alias

**Implementation:**
```python
parser.add_argument("--version", dest="baseline_version_deprecated", help=argparse.SUPPRESS)

if args.baseline_version_deprecated is not None:
    warnings.warn("--version is deprecated. Use --baseline-version.", DeprecationWarning)
    logger.warning("⚠️  DEPRECATED: --version will be removed in v2.0")
    args.baseline_version = args.baseline_version_deprecated
```

**Validation:**
- CLI test verifies both flags work
- CLI test verifies deprecation warning is logged

## Consequences

### Positive

1. **Deployment Flexibility:** Can run without NumPy in minimal CI
2. **Statistical Rigor:** Bootstrap CI quantifies uncertainty
3. **Operational Safety:** Backend mismatch detection prevents false positives
4. **Resource Protection:** DoS prevention via input bounds
5. **Gradual Migration:** Backward compatibility shims allow phased rollout
6. **Comprehensive Validation:** 59+ tests ensure correctness

### Negative

1. **Baseline File Growth:** Bootstrap CI adds ~2 fields, ~20% size increase
2. **Complexity:** More exit codes require updated CI scripts
3. **Performance:** Pure Python 50x slower (mitigated: only for small datasets without NumPy)

### Neutral

1. **Deprecation Warnings:** `--version` logs warnings until v2.0
2. **Schema Evolution:** v1.7 baselines have extra fields (v1.0 ignores them)

---

## Rollback Plan

If v1.7 causes production issues:

1. **Restore v1.0:**
   ```bash
   cp archive/scripts/performance_ledger_v1_0_backup.py tools/performance_ledger.py
   ```

2. **Revert CI scripts:** Remove `--strict`, restore `--version` flag

3. **Report issue:** Escalate to Architect with error logs

**Rollback Risk:** LOW (v1.0 backup preserved, all v1.0 tests still pass)
